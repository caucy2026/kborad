# KBoard Android 商城发布

来源：用户提供的 `kemi-skills-main/kemi-market-publish/SKILL.md` 及其 `references/release-contract.md`，2026-09-12 按用户要求仅提取 Android 和适用的通用发布规则。原始文件不修改。

## 范围与授权

- 仅处理 KBoard 输入法 Android APK 在 KEMI 商城的上架发布，`os_type=android`，应用身份为 `com.newlink.kemi.kboard`；不适用于 Windows、macOS 或其他端、其他应用。版本读取最终 APK 标准字段，禁止从文件名推算。
- 从项目正式发布工作流接收已测试、已审批的同一个 Release APK、`release.json` 和验收记录。上传前重新核对 SHA256；正式候选包不重新构建或签名，不绕过失败/缺失的测试。若用户明确要求两轮升级验收，可另建仅增加版本字段的测试包，但它不是正式候选包。
- 创建应用、更新记录、上传、上架均为生产写操作，需要当前任务明确授权。读取此 skill 或建立发布流程不代表已获发布授权。
- 管理员凭证、Bearer token、上传 token、签名私钥不得进入 APK、Git、日志或报告。凭证通过安全交互提供；临时凭证使用仅当前用户可访问的文件，任务结束清理。不能把 Linux 文件模式直接当作其它环境的有效权限控制。
- 执行前完整阅读 [Android 发布接口参考](references/android-release-contract.md)，并核对其中列出的官方在线文档。在线合同与副本冲突时先停止写操作，报告差异；不要用猜测字段发布。若任务包含“正式候选版预发布 → 下一版升级复测 → 撤销测试版 → 正式发布”，还须阅读 [两轮升级发布流程](references/staged-upgrade-release.md)。

## 发布步骤

1. 校验包名、APK versionName/versionCode、arm64 ABI、非 debuggable、平台签名及与上一线上包的覆盖升级兼容性；计算精确字节数与 SHA256。
2. 按 `(package_name, os_type)` 查询：唯一记录则更新原 app_id；没有记录才创建；多条记录停止处理。完整读取分页并作精确匹配，不能把关键词首页没有命中当作不存在。
3. 普通升级必须 `new_version_code > online_version_code`；展示版本为 X.Y.Z。元数据修复与版本发布分开，不能通过重复创建或改包名绕过校验。
4. 使用 Android 专用 `apk-token → CDN 上传 → apk-complete` 流程。请求体和响应以在线 Android 文档为准。完成响应的 URL、字节数、SHA256、解析出的包名和版本必须与本地包一致。
5. 创建/更新时保留已有描述、图标、分类、截图等非本次修改的字段；完整填写版本、HTTPS 下载地址、SHA256，以及同一精确大小的 `file_size` 十进制字符串和 `file_size_bytes` 整数。每次预发布或正式上架均按下方规则填写“更新说明”和“强制更新”，不要虚构评分、下载量或未验证能力。
6. 复查开发者记录、商城公开详情、实际可点击的下载入口、CDN 下载文件，并在指定 H730 测试机验证从商城完成覆盖升级及数据保留。
7. 使用上一线上 versionCode 验证可发现新版本；使用本次 versionCode 验证不再提示同版本更新。请求显式携带 `os=android`。
8. 核验下面的 KBoard 专用更新链路，记录结果、应用 ID、commit、APK 哈希、审批证据、商城回执及局限，清理临时凭证。正式上架后按“正式发布记录与 GitHub 归档”完成记录和远端核对。

若采用两轮升级验收，上述步骤中的正式上架须延后到两轮真机升级都通过且测试版草稿撤销之后；不能把较高版本码的测试包发布为正式版，也不能重新构建原候选包替代其已验收字节。

## 正式发布记录与 GitHub 归档

- **唯一的版本变更记录是仓库根目录现有的 `cl.md`**，不另建版本流水账。只有商城“保存并发布”成功且线上详情、下载包与候选 APK 核对一致后，才在 `cl.md` 顶部新增 `商城正式发布` 条目；预发布、设备安装和仅升版本号的测试包不得写成正式发布。
- 条目写明发布日期、上一商城正式版与本次正式版的标准 versionName/versionCode、相对上一正式版的主要改动和商城“更新说明”原文、完整 GitHub 源码 commit、包名、APK SHA-256、商城应用 ID／发布回执或可核验的详情链接、验收结果及未通过或未测项目。详细测试和商城回执可另存 `release/<版本>/` 作为证据，但不能代替 `cl.md` 的正式发布条目；不得提交凭证、签名文件或含敏感信息的日志。
- 正式发布任务包含将该条目及获准归档的证据**显式暂存、提交并推送到根仓库 `origin/main`**。推送前核对当前分支、远端更新和待提交差异，排除无关工作区改动；遵守仓库仅用 `main` 的约定。推送后重新读取远端 `main`，确认正式发布条目、源码 commit、版本号及哈希可被另一台机器查询。若推送或远端核对失败，保留已发布商城的事实并明确标记“GitHub 归档待完成”，不得报告整个发布流程已闭环。
- 下一次发布以商城当前线上正式版为准，再用 `origin/main` 中最新的 `商城正式发布` 条目核对上次版本及改动；两者不一致时先查清并修正记录，不凭候选构建或设备安装记录推断上一个商城正式版。

## 商城发布栏位

- 每次点击“预发布”或“保存并发布”前，在商城“更新说明”中写明本次 APK 的标准版本号，并用**至少三句完整的话**概述相对上一版本新增的功能或修复的问题。根据实际代码差异、`cl.md` 和测试记录撰写，不编造改动；提交后核对商城保存的说明。若是仅升版本号的升级测试包，仍写明版本号，并用至少三句话如实说明只改版本字段、没有新增功能或问题修复、仅用于升级链路测试，不把旧版改动冒充本版改动。
- 商城“强制更新”栏位在每次预发布和正式上架时**默认选择“可取消”**；只有用户明确要求本次发布“强制更新”时，才选择“强制更新”。提交前核对选择，提交后核对保存结果。此栏位是商城发布元数据，不等于授权 KBoard 阻断输入或实现静默安装。

## KBoard 更新职责（用户已确认，优先于原通用 skill）

- KBoard 设置 APP 前台启动后异步自动检查更新；仅在 `has_update=true` 且远端整数版本高于本地时主动提示。用户所说“后台控制”是后台提供更高版本，不需要独立弹窗开关。关于页“当前版本”行可显示更新红点；短按有新版时进入商城、无新版时提示已是最新版、检查失败时可重试。长按约 8 秒的工程入口须保持独立，不把短按误作工程入口。
- 用户点击提示中的“前往 KEMI 商城”跳转该应用详情页，再由用户在商城手动升级；可选择稍后处理。
- KBoard 不下载 APK、不调用安装器、不静默安装，也不新增安装权限或下载/安装状态机。下载校验和安装由 KEMI 商城负责，并由发布验收验证真实结果。
- 普通更新也可主动提示，不以 `force_update` 为提示前提；强制更新阻断输入或主流程需要另行授权。
- 后台检查失败静默记录脱敏诊断，不能影响输入或伪装成“已是最新版本”；无更新时不显示提示。同一版本用户已忽略后不重复打扰，新版本再提示；网络失败采用有上限的退避，不能连续弹窗。
- 商城包名、详情页 Intent/deep link、app_id/包名参数必须来自官方合同或商城源码。不得猜测通用 market URI 可由 KEMI 处理，不执行服务端任意 Intent。
- 商城缺失、版本不支持跳转或跳转失败时明确提示；不回退为键盘下载 APK 或静默安装。

## 完成判定

构建成功、上传成功、更新接口成功均不等于正式发布完成。必需同时取得签名/版本证据、商城记录与详情一致、下载字节与哈希一致、正反向更新检查、更新提示或版本入口跳转商城、真实升级结果，以及 `cl.md` 正式发布条目在 GitHub `main` 可查。两轮流程还须证明测试版草稿已撤销、最终线上版本和正式候选 APK 一致；主动弹窗未在第二轮复现时如实记录，不得用版本入口跳转结果冒充主动弹窗通过。未通过时明确区分已完成步骤和阻断项。
