# KBoard 两轮在线升级后正式发布

适用：用户明确要求先以商城预发布验证正式候选版，再用仅增加版本号的测试包证明该候选版仍可在线升级，最后撤销测试版并发布原正式候选版。此流程是用户选择的特定验收方式，不代替其它发布门禁或发布授权。商城 API 或管理界面均可使用，以执行时官方在线合同为准；不要从过去的界面坐标或 app_id 推断当前状态。

每次提交 A 或 B、预发布或正式上架，均执行主技能的“商城发布栏位”规则：更新说明写版本号和至少三句真实变更说明；未被用户指定强制更新时选“可取消”。B 若仅修改版本字段，不编造新功能或修复。

## 开始前冻结两份身份

- 查询现有 `(package_name=com.newlink.kemi.kboard, os_type=android)` 的唯一应用记录、线上版本和待审草稿。记录正式候选包 A 的源码 commit、APK 标准 versionName/versionCode、字节数、SHA-256、平台签名证书、sharedUserId、ABI 和本地保管位置。重新上传 A 时必须是同一字节文件。
- 确认测试 H730 的真实设备身份、目前已安装版本、商城版本与登录状态、默认输入法及 UID。预发布包只对具备待审版本可见权限的商城账号显示；若商城详情仍显示旧草稿，刷新/重新启动商城并核对详情，不可仅凭后台“审核中”认定设备可升级。
- 完成所需构建、JVM、Release lint、APK 门禁及获授权的功能验收。签名凭证只从批准的私密位置读取，不记录口令。确认商城预发布、撤销和正式发布均在本任务授权范围内；若没有授权，就停在相应写操作之前。

## 严格顺序

1. **A 预发布。** 在原应用记录“提交新版本”，上传 A；等待商城服务端完成解析，逐项核对包名、版本名、版本码、SHA-256、精确字节数和下载地址。保留原图标、分类、描述、展示平台及其它非本次修改的元数据。选择“预发布”，核实待审草稿是 A，线上旧版本保持不变。预发布不是正式发布。
2. **旧版 → A。** 在授权测试机上用旧版 KBoard 启动设置 APP，观察主动提示/红点；点提示“前往 KEMI 商城”或关于页“当前版本”入口，确认打开的是 KBoard 的商城详情。使用商城“更新”完成真实在线安装，不用 `adb install` 代替。安装后读取活动包版本、安装来源、UID、默认 IME、数据保留状态，并从设备回读 APK 与 A 比对 SHA-256；从 CDN 下载的包也核对字节数和哈希。若主动提示因检查缓存未出现，可用版本入口验证跳转，但把主动提示记为未复测。
3. **构建 B，仅改版本字段。** 在隔离的干净源码工作区，从 A 对应源码创建测试版 B，只递增 APK 标准 versionName/versionCode，确保 B 的 versionCode 高于 A。检查源码 diff 仅包含版本字段；不把功能改动混入 B，也不把 B 的测试源码提交为正式主线。按 KBoard Release 构建技能完成同一平台签名、arm64、非 debuggable、JVM/lint/APK 验证。B 的构建 commit 与 A 分别记录；B 不取代 A 的签名文件或已冻结 APK。
4. **B 预发布并 A → B。** 在同一应用记录上传 B，核对服务端解析出的完整身份后选择“预发布”。提交新版本可能替换上一份待审草稿；必须确认待审版本为 B、线上仍是旧正式版，而 A 文件仍安全保留。测试机从已安装 A 通过 KBoard 入口跳到商城 B 详情，点商城“更新”完成安装。核对活动版本、安装来源、UID、默认 IME 与设备回读 APK 哈希等于 B；记录任何启动弹窗、红点和商城缓存的实际结果。
5. **撤销 B，再正式发布 A。** 只有两轮真实在线升级都通过，才撤销 B 的待审草稿并核实待审项消失、线上版本未被改动。随后在原应用记录重新上传冻结的 A，核对服务端 SHA-256/大小/版本与第 1 步完全一致，再选择“保存并发布”。最后核实线上版本是 A，且没有 B 待审草稿；下载线上正式包比对 A 的哈希。按官方更新接口再查旧正式版→A 有更新、A→A 无更新、已装 B 不会被提示降级。不得把 B 发布为正式版，也不得在正式发布前跳过撤销。任一步失败即停止后续发布，保存失败证据。

## 证据与设备收尾

- 归档 A/B 的源码差异、构建与测试门禁、两次商城页面状态、两次升级前后 `dumpsys package`、默认输入法、安装来源、CDN/设备回读 APK 哈希、B 撤销与 A 正式上架结果。每项测试标注实际执行或待人工验证，不把跳转成功写成升级成功。
- B 已安装到测试机且 versionCode 高于正式上线的 A 时，普通覆盖安装不能安全降级。保留设备为 B 并告知用户；不卸载、`pm clear`、恢复出厂或尝试降级，除非另获明确授权及数据处理方案。
- 撤销草稿不等于已上传 CDN 文件立即不可访问；须区分“商城不再提供 B 更新”与“历史下载 URL 失效”，不作未经验证的删除承诺。
- A 正式上架并完成线上核验后，按主技能的“正式发布记录与 GitHub 归档”更新根 `cl.md`，归档 `release/<A版本>/` 的详细证据，并提交、推送及复核远端 `main`。B 预发布或撤销只写入测试证据，不得冒充商城正式发布。若 GitHub 归档受阻，准确报告商城状态及待补的远端记录。

2026-09-24 旧流程记载的实例：A=1.4.5/222，B=1.4.6/232；16.24 真机依次完成 1.4.4→1.4.5、1.4.5→1.4.6，撤销 1.4.6 草稿后正式发布原 1.4.5。旧流程所指的 `release/1.4.5/market/upgrade-and-publication-20260924.md` 当前未包含在仓库中；下一次发布仍须重新核对商城线上正式版及其证据，不能仅凭此历史实例认定当前线上状态。上述版本号、设备地址、商城 app_id 和 UI 坐标都不是未来发布的固定值。
